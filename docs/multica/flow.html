闸门一：合不合这个 PR

AI 改代码的地方，人只看这一眼：diff 改了什么、测试有没有被偷偷删、验收标准对不对得上。这一步没有捷径——把它自动化掉，等于让写代码的人自己判断该不该上线。

7

闭环回到第 1 步

同一个链接，不需要重新安装

玩家下一轮反馈又进第 2 步。同一条反馈从「收到」到「上线」全程挂在一个 issue 上，谁改的、凭什么发、发的是哪个版本，都能倒查。

旁路（不占主线）：周一 10:00 制作-Producer 把一周的反馈按主题聚类，证据够（≥2 条同类）才写规格 issue 派给开发，不够就留着不立项。

你在这条链上只出现三次

入口

定需求时：写清验收标准。一句话说清要什么，再说怎么算做完（比如「分享按钮：微信里能发到会话和朋友圈，卡片带最高分；网页端退化成复制链接」）。

这条必须你写。让 agent 自己写验收，它会照着自己做得到的事写。

合并

PR 出来时：看一眼 diff 再合。不用逐行读，但要确认三件事：改动范围是不是这件事、测试是真加了还是被改了、有没有夹带别的改动。

仲裁

issue 变 blocked 时：拍一下。agent 会把卡在哪一步、有哪几条路、各自代价写清楚。你只需要选一条。

已通

玩家反馈 → 落库 → 客服建 issue → 指派开发。3 条真反馈变成了 CANO-13 / 14 / 15，反馈状态也回写了。

依据：curl :8787/api/stats 显示 3 条都已是 issue_created。

已通

构建 → 发布 → 线上。web 14 KB / 微信小游戏 11 KB，Pages 由 Actions 部署，页面与产物都 200。

依据：GitHub Actions 三次全绿；Pages 用真浏览器打开过，无报错。

卡住

第 4 步「开发提交代码」不通：agent 能把代码改对、三条验证全绿，但写不进 git 索引，所以出不了分支和 PR。CANO-13 与 CANO-15 因此停在 blocked。

两个原因叠在一起：本机 git 2.39 太老（这套工作区续跑要 2.40+）；agent 的权限模式是「问」，无人值守时「问」等于「拒」。git 已装到 2.56，等 Multica 重启后 daemon 才用得上。

没接

线上反馈收不到：Pages 是纯静态，没有后端。要先把反馈台放到公网，再把地址打进构建。

登录与内购只有接口和占位实现，没对接任何商店。

# 入口与落账规则

这套工厂有四个说话的地方，但只认一个账本。

## 四个入口

| 入口 | 谁在用 | 谁来落账 |
|---|---|---|
| A. DSH 会话（就是现在这种对话） | 你，跟 AI 边聊边想 | 我（会话里的 AI）直接调 `multica issue create` |
| B. Multica 里和 agent 聊天 | 你，在工单板旁边顺手问 | 跟你对话的那个 agent |
| C. Multica 里人手写 issue | 你，想得很清楚时 | 你本人，写的就是账本 |
| D. 游戏里的反馈按钮 | 玩家 | 客服-CS（每 20 分钟扫一次） |

入口是给人方便的，**不是四个系统**。判断标准只有一条：

> 任何入口说出来的事，只要没落成 issue，就等于没发生。
> 聊天记录不算账，便签不算账，我口头答应你也不算账。

这条不是洁癖。AI 会话结束就没了记忆，聊天里说过的需求如果没有 issue，三天后就没有任何人知道它存在过——包括我。

## 落成什么

| 内容 | issue 标题前缀 | 状态 | 标签 |
|---|---|---|---|
| 玩家报的 bug | `【Bug】` | todo | `source/player` |
| 玩家想要的功能 | `【建议】` | backlog | `source/player` |
| 你提的需求 / 想法 | `【需求】` | backlog | `source/owner` |
| 聊天里冒出来、还没想清的点子 | `【想法】` | backlog | `source/chat` |
| 制作 agent 写完规格的 | `【规格】` | todo | `spec` |

正文最低要求三行：**要什么、怎么算做完、谁提的**。三行都写不出来，说明还没想清楚，那就先留 `【想法】`，不进开发。

## 落账前必须先搜

```bash
multica issue search "<关键词>" --project $PROJECT_ID --output json
```

同一条东西第二次出现时不要新建，在原 issue 下评论「又提了一次 + 来源 + 原话」。
重复的 issue 比漏掉的 issue 更贵——它会让人以为有两件事要做。

## 四个入口怎么串成一条线

```
你（DSH 聊天）──┐
你（Multica 聊天）─┼─▶ 落账 ──▶ issue（唯一账本）──▶ 分流
你（手写 issue）──┤                 │
玩家（游戏内）───┘                 ├─ bug ─────────▶ 开发-Dev 直接修
                                   ├─ 想法/需求 ────▶ 制作-Producer 每周出候选
                                   └─ 规格 ─────────▶ 开发-Dev 按规格做
```

分流之后又汇回同一条：PR → 你合 → 质检 → 发布 → 反馈状态回写。

## 我这边的纪律

在这个会话里，你随口说一句「应该加个排行榜」，我要做的不是「好的记下了」，而是当场落一条 `【需求】` issue 并把编号报给你。做不到这一点，这个入口就是假的。

判断要不要落账：**只要它可能变成一个要花人力的动作，就落。** 纯讨论（「你觉得排行榜有意义吗」）不落，但它一旦变成「那就做吧」，立刻落。

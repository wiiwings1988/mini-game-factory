# 模板边界：哪些进模板、哪些是插槽、哪些只属于某个实例

> 判据一栏都是**可复算的命令**，不是结论。命令在仓库根目录跑。
> 落盘日期 2026-10-31，基线 HEAD `0aac31f`（开工时是 `6740b57`，中途有人补了 `.gitignore`，见第三节末）。
>
> **本文是派生指南，不进模板。** 它进的是「实例 0 的文档」，派生时留在原件不动。

## 三句话结论

1. **能进模板的只有「骨架 + 合同」，不是「装满东西的仓库」**：引擎、平台契约、脚本、CI、五个岗位的合同能原样复制；游戏本身、Multica 实例号、仓库地址、端口只属于某个实例。
2. **今天派生一个新实例，`scripts/build.mjs` 会直接崩**——它把 `apps/web`、`apps/wx`、样板游戏写成了硬编码路径（证据见 §4）。所以模板必须先做成「空骨架 + 一个样板」，二选一，不能两头都要。
3. **派生门今天不存在**：CI 只跑三项（安装/类型/单测/构建），且单测在「零测试文件」和「一条空测试」两种情况下都可能给绿（证据见 §5）。

## 2. 做成插槽（每品类不同，占位符 / 生成器变量）

判据：**换品类时，这个文件的内容必然要变；但它变的方式是有结构的（几个字段），不是重写。**

| 插槽 | 现在的值 | 该长成什么样 | 证据 |
|---|---|---|---|
| 项目名 / 产品名 | `mini-game-factory`、`小游戏工厂 Mini Game Factory` | 生成时注入 | `grep -rn "小游戏工厂" --include=*.json --include=*.md .` 十几处散落 |
| 仓库地址 | `https://github.com/wiiwings1988/mini-game-factory` | 从 `git remote get-url origin` 推，或生成时问一次 | `tools/multica/apply.mjs:61`、`scripts/smoke.mjs:13`、`docs/multica/agents/release.md:46` 三处硬编码 |
| Multica 工作区 / 项目 | `e9fe338e-…`（老人星）、`acbea365-…`（小游戏工厂） | 环境变量（`apply.mjs` 已支持 `MULTICA_WORKSPACE_ID`，但默认值写死实例号） | `tools/multica/apply.mjs:19-20` |
| 反馈台端口 | `8787` | 端口分配表 | `tools/feedback-service/src/server.mjs:33`、`scripts/smoke.mjs:14`、`scripts/preview.mjs:19`、`apps/web/vite.config.ts:28` 四处 |
| 游戏目录名 | `games/arcade-dodge` | 生成时给名字 | `scripts/build.mjs` 直接拼 `apps/web`、`apps/wx` 路径 |
| 岗位集合 | 五个：策划/PM/开发/质检/发布 | 岗位名与文档名可配 | `docs/multica/factory.json`（5 条 `agents` + 4 条 `autopilots`） |
| 定时节奏 | `*/20`、`0 3`、`0 21`、`0 10 * * 1` | 跟团队作息挂钩，生成时问 | 同上 `factory.json` |

**一个可以直接跑的插槽检查**（生成新实例后、跑门之前先跑这个）：

```bash
# 实例值残留扫描：命中即说明该实例还是从实例 0 抄的，没做插槽化
grep -rn "e9fe338e\|acbea365\|wiiwings1988\|小游戏工厂\|8787" \
  --include=*.mjs --include=*.json --include=*.yml --include=*.md --include=*.ts . \
  | grep -v node_modules | grep -v '^./docs/multica/agents/_retired/'
```

今天跑这条命令（不含 `docs/factory/` 这三份新文档、不含已被 `.gitignore` 挡掉的 `.multica-state.json` 与 `logs/`），命中 **13 个 tracked 文件**：

| 类别 | 文件 | 命中什么 |
|---|---|---|
| 脚本里的默认值 | `tools/multica/apply.mjs` | 工作区号 `e9fe338e…`、仓库地址 |
| | `scripts/smoke.mjs` | Pages 地址、反馈台端口 8787 |
| | `scripts/preview.mjs` | 反馈台端口 8787 |
| | `tools/feedback-service/src/server.mjs` | 反馈台端口 8787 |
| | `apps/web/vite.config.ts` | 反馈台端口 8787 |
| 岗位合同 | `docs/multica/agents/release.md` | Pages 地址、端口 |
| 运行手册 | `docs/multica/README.md`、`README.md`、`ops/README.md` | 端口、项目名、工作区号、仓库地址 |
| 配置 | `docs/multica/factory.json` | 项目名「小游戏工厂 Mini Game Factory」 |
| 历史记录 | `docs/multica/验收记录.md`、`docs/multica/agents/_retired/cs.md`、`_retired/producer.md` | 端口、项目名、实例号 |

**注意最后一行**：「历史记录」那三个文件**不该拔**——它们是这条线的真实履历，拔掉就变成了假的。所以插槽化的判据不是「grep 零命中」，而是「**活文件**零命中，历史文件允许命中」。这条区别如果不写进派生门，门会把历史记录也判成红的。

## 3. 做成依赖（版本化包，不复制）

判据：**有独立的外部真源、有人维护、版本可锁——复制进来只会让它跟上游分叉。**

| 依赖 | 现在怎么来的 | 为什么不复制 |
|---|---|---|
| `typescript` `vite` `vitest` `@types/node` | `package.json` devDependencies，`pnpm-lock.yaml` 锁 | 外部维护、版本敏感 |
| `pnpm` 自身 | CI 里 `pnpm/action-setup@v4` 锁 `version: 10` | 同上 |
| `multica` CLI | 本机二进制（`multica 0.7.1`），脚本用 `spawnSync("multica", …)` 调 | **不随仓库分发**，新实例要自己装；这是一条未写进 README 的隐性前置条件 |
| GitHub Actions | `actions/checkout@v4`、`pnpm/action-setup@v4`、`actions/setup-node@v4`、`actions/upload-pages-artifact@v3` | 平台侧版本化 |

判据命令：`node -e 'const p=require("./package.json");console.log(Object.keys(p.devDependencies))'` → 4 个依赖；`git ls-files node_modules | wc -l` → 0（依赖从不入 git）。

## 5. 派生门：今天为什么还不存在

### 5.1 现状：能跑的门

在 master 上实测（2026-10-31 20:50）：

```
$ pnpm exec tsc -p tsconfig.json --noEmit      → exit=0（无输出）
$ pnpm test
  ✓ packages/engine/src/__tests__/loop.test.ts (4 tests)
  ✓ packages/engine/src/__tests__/rng.test.ts (6 tests)
  ✓ games/arcade-dodge/src/__tests__/game.test.ts (10 tests)
  Test Files  3 passed (3)      Tests  20 passed (20)
$ node scripts/build.mjs
  [build] web: 4 files, 66.8 KB
  [build] wx: 22 files, 168.3 KB
  [build] manifest → dist/build-manifest.json
$ node scripts/smoke.mjs --site http://127.0.0.1:4173   → 4/5 通过，exit=0
```

### 5.2 派生的第一分钟就会崩

`scripts/build.mjs` 把实例路径写死：`const vp = join(root, "node_modules/.bin/vite")`，然后直接对 `apps/web`、`apps/wx` 跑（这两个目录属于实例 0，见 §4）。新实例如果没先塞一个游戏，第一次构建就退出 1。

注意这是**两个层面的问题**：
- **目录不存在** → 构建直接失败（今天就能看见）。
- **目录存在但里面没有游戏代码** → 构建会成功，产出一个空壳。`smoke.mjs` 会抓两条内容（`页面有游戏挂载点` 判 `id="game"`、`构建产物可取` 判 JS ≥ 5000 字节），所以空壳会被它抓到；但它**只对 web 产物做这个判断**，wx 产物只在 `build.mjs` 的 manifest 里记字节数（今天 22 files / 168.3 KB），没有任何门去核那个数字合不合理。**这条更危险，因为它不报错。**

所以派生门必须补的不是「让构建别崩」，而是「**构建出来的东西里得真有内容**」——判据用产物字节数下限，不是退出码。

### 5.3 门自己会静默变绿的三种情况（今日实测）

| 场景 | 实测结果 | 危险在哪 |
|---|---|---|
| 仓库里有 `src/` 但零测试文件 | `No test files found, exiting with code 1` → exit=1 | 好：会红 |
| 测试目录里有一条**什么都不测**的测试 | `Tests 1 passed (1)` → **exit=0** | **坏**：绿了但什么都没验 |
| tsconfig 的 `include` 指向不存在的目录 | `error TS18003: No inputs were found` → exit=2 | 好：会红 |
| `smoke.mjs` 全失败 | exit=1 | 好：会红 |
| **`multica` CLI 未安装** | `spawnSync` 返回 `status=null` + `error=ENOENT`；`apply.mjs` 只判 `result.status !== 0`，会把「没装」当普通失败抛出，看不出根因 | **坏**：报错指不到「你没装 CLI」 |

上面第 2 条是「派生门」必须防的第一种腐化：**绿 ≠ 验了东西**。修法不是加断言，是给门自己加计数——`vitest run` 的输出里有 `Tests N passed`，把 N 和一份下限表比对，N 掉到下限以下就红。

### 5.4 派生门的完整设计另见

见 `docs/factory/派生门.md`（八步一票否决、输出表、跑动时机、四条防腐烂办法）。

本文只留三条与「边界」直接相关的判据：
- 门的第 1 步是**白名单复制**（只复制 §1 那份清单），漏了会红；黑名单复制（复制全部再删垃圾）每次新增垃圾都会漏，且漏是静默的。
- 门的第 3 步是**把 §2 那条 grep 在派生目录里跑一遍**，命中即红。
- 门的第 6/7 步要带**下限**，因为 `vitest` 在「一条空测试」时会 exit 0（§5.3 实测）。

## 6. 待乔克拍板

**A. 模板做成「空骨架」还是「带样板」？**
- 空骨架：派生后 `build` 直接崩（§5.2 已实测），必须先塞玩法。但模板干净，不会把躲块这个玩法带进每条新产品线。
- 带样板：派生即可跑通全部门，新人第一天能看着成品学。代价是每个新实例都得先删一遍样板（约 429 行 + 两个入口）。
- 我的建议：**带样板，但样板是独立目录 `games/_sample/` 且派生时默认不挂入口**。这样门能过（有东西可构建），产品线也不会误以为是自己的游戏。

**B. 派生门跑在哪？**
- 本地一条命令（上面 §5.4 的形态）：派生时跑一次，几十秒。
- 或做成 CI 的定时任务：每周一跑一次派生，红了就说明模板腐化了。
- 我的建议：**先做本地命令**（派生本来就不频繁）；等派生频次上来了（比如一个月三次以上）再谈定时。

**C. 实例值什么时候拔？**
- 现在就拔（改 `apply.mjs`、`smoke.mjs`、`preview.mjs`、`server.mjs`、`vite.config.ts`、`release.md` 六处活文件 + 三份手册同步）：约 9 个活文件，历史记录那三个不动。
- 派生第一个新实例时再拔：那时有真实需求驱动，拔得准。
- 我的建议：**派生第一个新实例时再拔**，但今天先把命令写进这个文档（§2 那段 grep），让「拔没拔」有客观判据。

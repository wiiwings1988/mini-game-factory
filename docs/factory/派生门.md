# 派生门设计：从模板复制出一个空实例，跑一遍全绿，才算模板健康

> 落盘 2026-10-31，基线 HEAD `0aac31f`。
> **目前只有设计，没有实现。** 文里标「实测」的是今天真跑过的；标「未实现」的是还没写代码的。

## 一、要解决的真问题

模板腐化不是「哪天突然坏了」，是**悄悄变成错的**。它的四种形态，按发生概率排：

| 形态 | 长什么样 | 今天有没有 |
|---|---|---|
| 依赖漂移 | 派生时装出来的版本和实例 0 不一样，本地绿、新实例红 | 有（`pnpm-lock.yaml` 锁住了，但模板仓库自己的 lock 会跟着实例 0 的依赖走） |
| 插槽漏改 | 新实例里还写着别人的仓库地址、别人的 Multica 工作区、别人的端口 | **有**：实测 13 个 tracked 文件带实例值，其中 9 个是活文件、3 个是历史记录（不该拔）、1 个是配置（见《模板边界》§2） |
| 门变松 | 门还绿着，但验的东西越来越少（测试被删、断言被改成恒真、产物变空壳） | **有**：实测「一条空测试」就能让 `vitest` 给绿 |
| 实例值腐化 | 模板里硬编码了一份「本机路径/当前月份/某个人的账号」，半年后没人记得它为什么在这 | 有（4 处端口、3 处仓库地址、2 处工作区号） |

派生门就是**一次性把这四种都撞一遍**的那道闸。

## 二、门跑什么（八步，一步一票否决）

```
[0] 起一个干净目录（不在模板仓库里，也不在 ~ 下）
[1] 复制：只复制《模板边界》§1 那份「进模板」清单，逐条白名单，不写通配
[2] 注槽：七个插槽逐字段注入（项目名/仓库地址/工作区号/项目号/端口/游戏目录名/岗位集合）
[3] 残留扫描：把《模板边界》§2 那条 grep 在派生目录里跑一遍，命中即红
[4] pnpm install --frozen-lockfile
[5] 类型：pnpm exec tsc -p tsconfig.json --noEmit
[6] 单测：pnpm test，并且 Tests N ≥ 下限
[7] 构建：node scripts/build.mjs，并且两段产物字节数 ≥ 下限；wx 侧要有一个数
[8] 冒烟：node scripts/smoke.mjs，站点与反馈台都要通；反馈台用临时端口，不碰 8787
```

第 1 步为什么用白名单不用黑名单：黑名单（复制全部再删垃圾）每次新增垃圾目录都会漏；白名单漏了会红（找不到要复制的目录），**漏是显性的**。

第 4 步为什么必须 `--frozen-lockfile`：不加这个参数，派生会把 lock 悄悄改掉，于是「模板锁住的版本」和「派生真正装的版本」从此分开走，而这种分开不会报错。

### 门要输出的那张表

每次派生打一张这样的表给人看，人一眼能判断「这次派生跟上次有什么不一样」：

```
派生体检  2026-11-02  目标 /tmp/derive-abc123  模板 0aac31f
──────────────────────────────────────────────
[1] 复制      PASS   白名单 9 项 / 实际复制 9 项
[2] 注槽      PASS   7 个插槽 / 7 个注入点 / 0 个失败
[3] 残留扫描  PASS   命中 0 行（阈值 0）
[4] 安装      PASS   0.0s（缓存命中）/ lock 未变
[5] 类型      PASS   exit 0
[6] 单测      PASS   20 passed / 下限 20
[7] 构建      PASS   web 68.4KB ≥ 60KB / wx 172.4KB ≥ 150KB
[8] 冒烟      PASS   5/5 项 / 反馈台临时端口 3917
──────────────────────────────────────────────
结论：模板健康
```

最后一行那个「结论」必须由**每行都是 PASS** 算出来，不允许手写。

## 三、门多久跑一次

| 时机 | 跑不跑 | 为什么 |
|---|---|---|
| 真派生一个新实例时 | **必跑**，不绿不许开工 | 这是门唯一不可省的时机 |
| 模板自身有结构变更时（改 `scripts/`、改岗位合同、改 `factory.json`） | 跑 | 这些正是插槽和门定义所在 |
| 每周一次（定时） | **可选** | 依赖漂移（§一第一行）只有靠时间才能撞出来；但如果一个月才派生一次，每周跑就是浪费 |
| 每次 push | **不跑** | 派生是一次性动作，不是每次提交都会发生的事；塞进 CI 只是让每次 push 多花几十秒，验的永远是同一个仓库自己 |

我的建议：**开头几周按「结构变更时跑」+「每次真派生跑」**，不设定时。等真派生频率上来（一个月三次以上）再加定时——判据是「如果两周没跑过门，你会不会心里没底」，会，才值得上定时。

## 四、门自己不腐烂：四条硬办法

这一节是全文最重要的。门最大的风险不是「跑不动」，是**跑得动但已经不验东西了**。

### 4.1 下限表入库，不写进脚本

`docs/factory/gate-baseline.json`（**待创建**）：

```json
{
  "tests":   { "min": 20,   "why": "2026-10-31 实测 3 文件 20 条" },
  "build":   { "webBytes": { "min": 60000 }, "wxBytes": { "min": 150000 },
               "why": "2026-10-31 实测（build 跑两遍字节数会浮动：web 66847→68361，wx 168300→172375）" },
  "smoke":   { "minChecks": 5, "why": "2026-10-31 实测输出 5 项：站点200 / 游戏挂载点 / 产物可取 / 反馈台健康 / 反馈可写入等" },
  "tracked": { "min": 40,   "why": "git ls-files | wc -l = 66；派生后可少，少太多说明复制漏了" }
}
```

两条关于数字的纪律：
- **下限要留余量**。今天同一个仓库连跑两次 `build`，web 产物 66847 与 68361 字节、wx 168300 与 172375 字节——差 2% 左右。下限贴着实测值写，第一次重跑就会假红，人就会去调低它，调一次就再也拦不住真腐化。
- **每条下限都写 `why`**。半年后有人要调低某个数，先读那个 why，才知道当初它是拿什么量出来的。

为什么要入库而不是写成脚本里的常数：**入库了，它变成一次 commit，可以被 diff、被 review、被追溯「谁把下限从 20 改成了 19」**。写在脚本里的常数只会跟着「让它变绿」的需求一起被改掉，且没有痕迹。

### 4.2 负例自测（门里最重要的一条）

派生门带 `--self-test`：故意把东西弄坏，看门会不会红。四组负例，缺一不可：

| 故意弄坏什么 | 期望 | 防的是 |
|---|---|---|
| 删掉一个测试文件 | 单测那行必须红（N < 下限） | 测试被删但门还绿 |
| 把一条测试改成 `it("x", () => {})` | **必须红** | 今天实测这种空测试会让 `vitest` 给 exit 0 |
| 把 `id="game"` 从页面里删掉 | 冒烟那行必须红 | 空壳站点 |
| 往一个源文件里塞 `wiiwings1988` | 残留扫描那行必须红 | 插槽没注干净 |

**负例本身也会腐烂**：如果哪天 `games/arcade-dodge/src/__tests__/render.test.ts` 被删，负例里「删掉一个测试文件」可能删中就红了（好），也可能删不中而静默失效（坏）。所以负例必须断言「我确实弄坏了东西」——删之前先断言那个文件存在。

### 4.3 异源复核

门由**不是造模板的人**跑第一次。自己造的门自己验，等于没验。具体做法：派生的第一次交给岗位里的「质检-QA」跑，而不是造模板的人自己跑。

同理，模板本身的评审也要有个异源：`nightly-qa` 的 autopilot 已经在跑端到端冒烟，让它顺带跑一次派生门是零边际成本。

### 4.4 派生记录入库

`docs/factory/derivations.md`（**待创建**），一次派生一行：

```
| 日期 | 给谁 | 模板提交 | 插槽摘要 | 门结果 | 备注 |
| 2026-11-02 | 某产品线 | 0aac31f | 名称=… 端口=39xx | 8/8 PASS | — |
```

这份记录解决的是「门多久没跑了没人知道」——打开文件看一眼日期就知道。

## 五、今天实测过的门证据（不是设计，是真跑）

在 master 上：

```
$ pnpm exec tsc -p tsconfig.json --noEmit        → exit=0
$ pnpm test                                       → 3 files / 20 passed
$ node scripts/build.mjs                          → web 4 files 68361B / wx 22 files 172375B
$ node scripts/smoke.mjs --site http://127.0.0.1:4173 → 4/5 通过（站点无服务，其余 4 项 PASS）exit=0
```

四条静默风险的实测（决定了下限表该怎么定）：

```
零测试文件      → "No test files found, exiting with code 1"   exit=1   ✓ 会红
一条空测试      → "Tests 1 passed (1)"                          exit=0   ✗ 假绿
tsconfig 零输入 → "error TS18003: No inputs were found"          exit=2   ✓ 会红
smoke 全失败    → exit=1                                                 ✓ 会红
```

**结论：`vitest` 的退出码不足以判断「测试真的存在且真的在测」。** 下限表 + 负例是补这个洞的唯一办法。

## 六、待乔克拍板

**A. 派生门的「空实例」到底有多空？**

| 选项 | 派生后能跑通什么 | 代价 |
|---|---|---|
| 完全空（无游戏） | 构建会红，必须先塞玩法 | 门的第一步就得允许「构建失败」，等于门验不了构建那段 |
| 带一个最小样板（`games/_sample/`，不挂入口） | 全门能跑通 | 模板里永远带着一份样板代码，要维护它 |
| 带完整样板（就是现在的 arcade-dodge） | 全门能跑通，新人能看成品 | 每个新实例都要先删 429 行 + 两个入口，删漏了就成了「继承别人的游戏」 |

我的建议：**带最小样板**。理由：门如果验不了构建，它就不算门；而完整样板会把「躲块」这个玩法带进每条新产品线，将来清理的成本比维护一份样板高。

**B. 下限表放在模板仓库里，还是放在派生脚本里？**

| 选项 | 好处 | 代价 |
|---|---|---|
| 放模板仓库（`docs/factory/gate-baseline.json`） | 变更有 commit、可 diff、可追溯 | 每个派生出来的实例都带一份「别人家的下限」 |
| 放派生脚本（模板仓库外） | 新实例干净 | 改下限没人看得见，容易变绿 |

我的建议：**放模板仓库**，但派生时**不复制**这个文件——它是模板的健康基线，不是产品的。

**C. 现在做还是等真派生时做？**

- 现在做：约一天（写复制白名单 + 七个插槽注入 + 两条负例）。现在做的好处是「模板边界」这份分类刚落地，热的。
- 等真派生时做：不浪费；但那时会被「新产品的工期」推着把门做松。

我的建议：**先只做第 3 步（残留扫描）+ 第 4.2 条的两组负例**（半天），其余等真派生时补。理由是这两项对应今天已经确证的两种腐化（13 个文件带实例值 / 空测试假绿），其余四种是推演出来的。
